A production LLM server is not a function call. It is a transport system — passengers arriving at random, carriages that only leave when full, a depot behind a locked door, and a signalling scheme that decides who waits. Orientation

Why serving is a
queueing problem

On your laptop, running a model is one line: model.generate(prompt). In production that line is the least interesting part of the system.

The moment a second person shows up, three pressures arrive at once, and every design decision in chapter 3 is a response to one of them.

GPUs hate being idle, and they hate being polite. A forward pass over one sequence and a forward pass over sixteen sequences take almost the same wall-clock time, because decoding is bound by how fast you can drag weights out of HBM, not by arithmetic. Serving one request at a time on an H100 is like running a twelve-carriage train with one passenger in it. So you batch — and batching means somebody waits at the platform.

Humans measure quality in milliseconds-to-first-word. A ninety-second wait for a complete answer feels broken; the same ninety seconds feels fine if words appear from second one. So you stream — and streaming means the token that was just produced deep inside a worker process has to find its way back to one specific open HTTP connection, across a thread boundary, while fifteen other tokens do the same.

Models fall over. CUDA runs out of memory, a tokenizer chokes on an emoji, a kernel deadlocks. If that happens inside your web server, your web server dies with it. So you push the model into a separate process — and now every request has to be pickled across a pipe.

Batch, stream, isolate. Three pressures, six components, and four endpoints that each thread a different route through them. Here is the whole network on one page; everything that follows is a walk down one of these lines.

01
The Local Line · POST /basic_generate

One passenger,
one private taxi

The simplest endpoint in the chapter is also the most useful one to read first, because it shows you the whole spine of the system with the clever parts switched off.

Everything starts at the front desk. FastAPI's job here is small and deliberately boring: parse JSON into a typed object, hand it to something that knows about models, and serialise whatever comes back.

Read
get_llm is a lazily-initialised singleton behind a lock, wired into every route with Depends(get_llm). FastAPI calls it per request; the lock makes sure two simultaneous first-requests don't each build an engine. It is guarding against a race that main() then eliminates anyway by calling get_llm() before uvicorn.run — so in practice the engine is always already warm by the time a request lands. That is the right call: you do not want the first user of the day paying for a model load.

One detail worth a raised eyebrow: the lock is a multiprocessing.Lock, but the thing it protects is a module-level global inside a single process. Uvicorn's concurrency here is threads and coroutines, not processes; a threading.Lock is what this wants. It works, because a multiprocessing lock is also a perfectly good intra-process lock — it is just a semaphore you paid extra for. And if you ever did run uvicorn --workers 4, each worker would import the module fresh and get its own _llm and its own lock, so the multiprocessing flavour would buy you nothing there either.

Now the routes. There are four, and they are all three lines long, which is exactly how a serving API should look.

Signal faultThree of these four routes stall the whole server

Look at the shape: async def endpoint, calling llm.basic_generate(...), which is an ordinary blocking function that waits on a multiprocessing queue. Inside a coroutine, a blocking call does not yield — it holds the event loop hostage. While one /generate is grinding through a batch, uvicorn cannot accept a connection, cannot flush a stream, cannot answer a health check.

The fix is one keyword: drop async and let FastAPI run the handler in its threadpool, or keep async and wrap the call in await asyncio.to_thread(...). Only /generate_stream is written correctly, because everything it does is genuinely awaitable. Keep this in mind for the rest of the article — it is the difference between "a server" and "a script with a URL".

Booting the engine

The constructor is where the money is spent. Reading it tells you what the process will look like in htop ten seconds after start-up.

Cost
Five lines, three concurrency domains. After __init__ returns you have: the uvicorn process (event loop + threadpool), a background daemon thread inside it running requests_processing_loop, a forked process holding a transformers copy of opt-125m, and — in the same parent process — a complete vLLM engine holding its own copy of the same weights and, on a GPU, pre-allocating most of the VRAM for its KV cache. You pay all of that even if the only endpoint you ever call is /basic_generate.

That is a teaching artefact, not a recommendation. In a real service you pick one execution backend. But it is a useful accident, because it lets one file put the hand-rolled loop and the production engine side by side, and we will compare them directly in §05.

The taxi

And now the endpoint itself — five lines, and the most instructive thing about them is what they don't do.

No queue. No workload manager. No batching. It mints a Sequence with client_stream=None and loop=None, wraps it in a one-element list, and shoves it straight through the depot door. If ten users hit this endpoint at once, ten one-element batches go through the pipe one after another, and the GPU does the same amount of work it would have done for a single batch of ten. This is the "before" picture. Hold onto it.

Then there is that results[1][0], which is where a wire protocol leaks into application code. The worker process replies with a tagged tuple — ('complete', [...]) for a full generation, ('stream', [...]) for a single token step — so results[0] is the tag and results[1] is the payload. The streaming path unpacks it politely (result_type, results = self.result_queue.get()); this path just indexes into it. Two callers, two conventions, one queue. It is the kind of thing that is invisible until the day you add a third message type.

And the far end of that line is fifteen lines of Hugging Face:

Note
It creates model_cache/ and then never uses it — from_pretrained caches into ~/.cache/huggingface unless you pass cache_dir. A one-word fix (from_pretrained(model_name, cache_dir=self.model_dir)), and worth caring about the day your container's home directory is ephemeral and every restart re-downloads the weights.
02
The Express Line · POST /generate

Nobody leaves
until the carriage is full

Batching is the single highest-leverage idea in model serving, and it is entirely a scheduling problem. Not one line of it is about neural networks.

The unit that gets scheduled is a Sequence. It is a plain object and it is worth memorising, because vLLM, TGI and SGLang all have one with almost exactly these fields.

Read
Two of these eight fields are not about the model at all — loop and client_stream are a return address. The sequence carries, inside itself, the identity of the event loop that owns the HTTP connection that is waiting for it. That is how a token produced in a background thread finds its way home. Everything in §04 hangs off those two lines.

The WorkloadManager is the signal box. Two lanes in — one for blocking requests, one for streaming — and a registry so anyone can look a sequence up by id.

get_next_batch is thirty seconds of reading and repays it. It does not build a new batch; it tops up a standing one. If two sequences are already running and the queue holds five more, it admits two and returns a list of four. And it returns the list itself, not a copy — so the caller is holding a live handle on the scheduler's internal state, which is exactly why the result-handling loops downstream have to call remove_active_sequence rather than just rebuilding the list. This is a genuine design choice, not a slip: a batch that can be topped up between steps is one small step away from continuous batching, which is where §05 goes.

Here is that admission policy, running for real. This is the file's own code, unmodified — it imports nothing but uuid, queue and typing, so it runs in your browser as-is. Change batch_size, add more prompts, and re-run.

workload_manager.py · verbatim · CPython 3.12 on WebAssembly

Notice what the output shows: the batch never empties and refills in lockstep. Sequences leave, new ones slot into the gap, the carriage stays full. That behaviour is free here because we're only looking at the queue. The trouble starts when the model gets involved, because the model in this chapter cannot handle a batch whose membership changes mid-flight.

The blocking generate loop

The comment on line 13 is the honest one, and it is easy to skim past: the batch you execute may contain prompts that belong to someone else's HTTP request. That is not a bug — it is the whole point of a shared scheduler. Two users arrive within 50 ms of each other, their prompts land in the same queue, one call to execute_batch serves both, and each caller then picks its own results out by request_id. Your GPU did one pass instead of two.

It is also where the design starts to strain. The loop's exit condition tracks only your ids, but the work it drives is global; a caller can end up spinning through several batches of other people's traffic before its own is done. And with time.sleep(0.1) in an async def call chain, every one of those idle spins freezes the server. In a real engine this loop lives in a dedicated scheduler thread and the request handler just waits on a future.

What "static" batching costs you

Down in the worker, the whole batch is handed to model.generate(..., max_new_tokens=50) in one call. That single call is atomic from the scheduler's point of view: it returns when the last sequence in the batch is done. A four-word answer sitting next to a fifty-token answer waits for the fifty-token answer, and the GPU spends those steps computing padding.

03
The Depot · model_executor.py + model_worker.py

Behind the
locked door

The model does not live in your web server. It lives in a different process, and the only thing that crosses between them is bytes.

Three good reasons, in ascending order of importance.

  • The GIL. A torch forward pass releases the interpreter lock while it is in C, so it is not the disaster people assume — but tokenising, sampling, decoding and the Python-level batching loop all hold it. On a busy server that is enough Python to matter.
  • Blast radius. A CUDA OOM, a segfault in a fused kernel, a NCCL hang — in-process these take your HTTP server with them. Out of process, the parent notices a dead child and restarts it while still answering health checks.
  • Placement. One worker per GPU is the natural shape of the thing. Once the worker is a process you can pin it, give it its own CUDA context, and later replace "one process" with "eight processes across two nodes" without the API layer noticing. This is precisely how vLLM's Executor/Worker split is organised, and why it survives the jump to tensor parallelism.

The implementation is two queues and a process.

That is the entire protocol: put a (payload, is_streaming) tuple on one queue, block on the other until a (tag, results) tuple comes back. No request ids on the wire, no correlation, no timeout. It works because exactly one thing may be in flight at a time.

Single laneThe depot door is a mutex

result_queue.get() blocks, and nothing tags results with the batch they belong to. So if the streaming thread and a /generate caller both send work, whichever of them wakes up first takes whichever reply arrives first — possibly the other's. The system is only correct because in practice one loop drives it. Making this concurrent means either one queue pair per in-flight batch, or — the usual answer — a monotonically increasing request id on every message and a dispatch table on the way back.

The pickle asymmetry

Here is a detail that looks like sloppiness and is actually load-bearing. The two paths send different types across the boundary:

Why not send Sequence objects in both cases? Because a streaming sequence holds client_stream (an asyncio.Queue) and loop (a running event loop). Neither is picklable, and even if it were, a copy of an event loop in a child process is meaningless. So the streaming path strips the sequence down to the two fields the model needs — the text and the name — and leaves the return address behind in the parent, where it still works. The blocking path can afford to ship whole objects only because its sequences were constructed with None, None in those slots.

That is the general rule for any process boundary in a serving system, stated in miniature: send data, never handles.

The child's main loop is the smallest interesting piece of code in the chapter:

Note
Nothing ever puts None on that queue. __del__ calls terminate() instead — a SIGTERM, mid-forward-pass, with no chance to release a CUDA context or flush a log. And __del__ on a module-level singleton is not guaranteed to run at all at interpreter shutdown. A production version sends the sentinel, waits with a timeout, and only then escalates to terminate().

Inside ModelWorker.generate — the blocking path — it is ordinary Hugging Face, with one important line:

padding=True pads every prompt to the longest one in the batch. That is what makes a batch a rectangle, and a rectangle is what a GPU wants. It is also the reason batching has a limit: batch a 10-token prompt with a 500-token prompt and you have just asked the model to do 500 tokens of work for the short one. Real schedulers bucket by length for exactly this reason, and attention_mask is what stops the padding from polluting the maths.

Also note generated_texts contains the prompt plus the continuation — model.generate returns the full sequence and nobody slices the prompt off. So /generate echoes your input back to you with the completion glued on. Harmless; surprising the first time.

04
The Circle Line · POST /generate_stream

A token crosses
three worlds

This is the hardest thirty lines in the chapter, and the payoff for reading them slowly is that every streaming inference server you ever meet will look familiar.

A single token has to travel from a tensor in a child process to one specific open TCP connection in a parent process, without going near any of the other fifteen connections. It crosses two boundaries to get there, and they are boundaries of completely different kinds.

World 1 — the generator that waits

Protocol
SSE is not a framework, it is a text format: data: <payload>\n\n. Two newlines end a frame; the browser's EventSource (or curl --no-buffer) fires one event per frame. The payload here is JSON — {"token": " a", "sequence_id": "8310f5e1…"} — so the client can tell interleaved streams apart. That is why sequence_id is on the wire even though each connection only ever sees its own tokens: it makes the format multiplexable later, for free.

The finally block matters more than it looks. If the client hangs up mid-generation, the generator is closed, finally fires, and the sequence is dropped from the registry — so the scheduler stops producing tokens nobody is listening to. That is your cancellation story, and it is the reason to route streams through an async generator rather than a callback.

The asyncio.set_event_loop(loop) on line 2, however, is a no-op ritual — the coroutine is already running on that loop; that is where get_event_loop() in the route handler got it from.

World 2 — the loop that never sleeps

This is the engine's heartbeat, and it is running before the first request arrives.

Read the shape and ignore the details for a second: admit → one step for everyone → deliver → repeat. That is a decode loop. Every serious inference engine has this exact function; vLLM calls it step(). The difference is what happens inside.

Two things to notice. First, the batch is re-derived on every iteration, so a request that arrives between steps joins the very next one — no waiting for a batch to drain. That is continuous batching, arrived at almost by accident, and it is the genuinely good idea in this file.

Second, the try/except wraps the entire body and swallows everything. When get_sequence returns None for a sequence that was cleaned up on the previous step, seq.token_count raises AttributeError, the loop prints one line and starts over — silently abandoning the rest of that batch's tokens. Broad excepts around a scheduler are how streams mysteriously stall.

World 3 — one step, and the trap inside it

And in the workload manager, the other half of the trap:

The big oneNo KV cache, so every step redoes all of history

Put those two lines together. The sequence's prompt grows by one token each step, and each step re-tokenises that whole string and runs a full forward pass over it with use_cache=False. Generating n tokens therefore costs 1 + 2 + 3 + … + n token-positions of attention work instead of n. That is O(n²) where the standard answer is O(n).

At the chapter's max_tokens = 20 you will never feel it — 210 positions instead of 20. At 512 tokens it is 131,328 instead of 512: a 256× multiplier on your decode cost. This single flag is the entire reason the KV cache exists, and everything vLLM is famous for — PagedAttention, block tables, prefix sharing — is machinery for making that cache cheap to manage rather than machinery for making it exist.

Two more faults, both about batching

They only bite when more than one sequence is in flight, which is exactly the case this code was written for.

FaultRight-padding breaks logits[:, -1, :]

The batch is padded to its longest member. OPT's tokenizer pads on the right by default, so a short sequence's row looks like […real tokens…, PAD, PAD, PAD]. Taking position -1 then reads the logits produced after three pad tokens, not after the sequence's real last token. The attention mask stops padding from being attended to, but it does not move the position you indexed.

The fix every batched-decode implementation uses: tokenizer.padding_side = "left", so every sequence's real last token lands at index −1. Alternatively, gather per-row at attention_mask.sum(1) - 1. Without one of these, short sequences in a mixed batch generate noise.

FaultThe stop condition can never be true

is_finished compares tokenizer.decode(tok, skip_special_tokens=True) — which deletes special tokens, so EOS decodes to the empty string — against tokenizer.eos_token, the literal string "</s>". "" == "</s>" is never true, so a sequence never reports itself finished. Streams terminate solely because seq.token_count > self.max_tokens trips at 20. Compare token ids, not decoded text: next_token[i].item() == tokenizer.eos_token_id.

None of this makes the chapter wrong. It makes it a very good specimen: the architecture is right, and the bugs are precisely the ones that a real engine's complexity exists to prevent. Watching the machine run makes that concrete — press play.

The Fast Line · POST /generate_vllm

Six lines that
replace two hundred

Having built the whole thing by hand, the chapter then shows you the version you would actually ship. It is the shortest method in the file.

No queue, no executor, no worker, no thread. All four of those things still exist — they are just inside vLLM now, written by people who do this full time. What you get for the trade is worth enumerating, because each item maps to something we found broken above.

What vLLM addsWhich fault it removesOrder of magnitude
KV cache (paged)use_cache=False re-attending the whole prefix each stepO(n²) → O(n)
Continuous batchingStatic model.generate() holding slots for finished sequences2–4× throughput
PagedAttentionReserving max_len of contiguous KV per sequence~4% waste vs 60–80%
Prefix cachingRe-prefilling a shared system prompt for every requestlarge, workload-dependent
Correct batched samplingRight-padding, decoded-string EOS comparisoncorrectness, not speed
CUDA graphs, fused kernelsPython launch overhead dominating small decode steps10–30% at low batch
Chunked prefillA long prompt's prefill stalling everyone else's decodetail latency

PagedAttention deserves its own picture, because the idea is stolen wholesale from operating systems and once you see that, it stops being mysterious. The problem: you don't know how long a generation will be, so a naive cache reserves the maximum for every sequence. Almost all of that reservation is never used, and what is free is scattered in pieces too small to hand out. It is heap fragmentation, in HBM, at gigabyte scale.

The solution is virtual memory. Cut the cache into fixed-size blocks of, say, 16 tokens. Give each sequence a block table mapping its logical positions to whatever physical blocks happen to be free. Allocate a new block only when the sequence actually fills the last one. Two sequences sharing a system prompt point at the same physical blocks until one of them diverges.

CaveatThis endpoint is still wired up wrong

vllm.LLM.generate() is the offline batch API. It is synchronous, it does not admit new work while it runs, and calling it from an async def route blocks the loop exactly as before. The serving API is AsyncLLMEngine (or just running vllm serve and putting your gateway in front of it), which exposes an async generator per request and does the continuous batching across concurrent callers. As written, the endpoint demonstrates vLLM's kernels but throws away its scheduler.

The Interchange · multi_model_serving/

Many models,
two platforms

The second service in the chapter answers the opposite question. Not "how do I serve one model to many people", but "how do I serve many models from one box that only has room for two".

This is the everyday shape of internal ML platforms: forty small models, sporadic traffic on most of them, and a GPU that fits three. The answer is a cache with an eviction policy — and once you say that out loud, the design writes itself. Five files, and each one is a single well-known pattern.

The registry first, because it sets the vocabulary for everything else.

Design
Splitting id from name is the good decision in this file. Clients hold an opaque uuid; the platform is free to repoint that uuid at a new checkpoint, a different framework, or a remote Triton instance without anyone changing their code. A real store adds a weights URI, a hardware requirement, a warm-up input, and a health probe — but the shape is already right.

Then the cache. Python's OrderedDict gives you LRU in two method calls, which is why this class is forty lines instead of four hundred.

Three lines of policy — move_to_end on a hit, popitem(last=False) on a miss-with-a-full-cache, insert at the end on a load — and you have a working model cache. Everything else in the method is bookkeeping.

Signal faultEviction drops a reference, not a model

popitem and delete_worker remove the two dictionary entries. Whether the several gigabytes of weights actually leave the GPU depends on refcounts and, on CUDA, on the caching allocator — which holds freed blocks in its own pool and will not return them to the driver until you ask. A real eviction path explicitly drops the module, runs gc.collect(), calls torch.cuda.empty_cache(), and only then admits the next model. Otherwise "max 2 models" silently becomes an OOM at model 3.

FootgunTwo sources of truth, and a shadowed class attribute

Residency is recorded twice — in manager.model_cache and in engine.workers — and a cache hit reads from the second one. They only agree because every mutation happens to touch both. Worse, ModelEngine declares workers = {} at class scope and then shadows it with self.workers = {} in __init__. Harmless as written, but the class-level dict is a shared-mutable-default waiting to be found by the first person who removes the line in __init__.

The factory and the strategy

The last two files are textbook, and pleasantly so.

That two-line ordering in TransformerWorker.__init__ is the most Python thing in the chapter. The base class calls _load_model() from inside __init__, so by the time the subclass's own initialisation would normally run, its method has already executed. Any attribute the override touches has to exist first. Calling overridable methods from a constructor is a known hazard in every OO language; here it costs one comment and a re-ordered line, and it will bite whoever adds the fourth worker.

One more, worth catching: TorchVisionWorker._load_model ignores model_metadata.name entirely and hard-codes mobilenet_v2. The registry says "pytorch/vision:mobilenet_v2"; the loader does not read it. Add a second torchvision model to models.json and you will silently serve MobileNet under its name.

Triton — when the depot is someone else's

The fourth worker doesn't load anything. It asks a dedicated inference server to.

The interesting part is that _load_model / __del__ line up exactly with Triton's --model-control-mode=explicit repository API. Your ModelManager's LRU decisions become load and unload calls against a server that is doing its own memory accounting — you keep the policy, Triton keeps the mechanism. That is the correct division, and it is what you would build against any external runtime.

What Triton brings that the hand-written workers don't: multiple framework backends behind one wire protocol (KServe v2), server-side dynamic batching with a configurable queue delay, multiple model versions live at once, instance groups pinning replicas to specific GPUs, and ensembles that chain preprocessing → model → postprocessing inside the server. 07
Signal failures

Everything wrong
with this code

Collected in one place, in the order I would fix them. None of this is a criticism of the chapter — teaching code that is also production code teaches nothing. But knowing which corners were cut is most of what the chapter is for.

/basic_generate, /generate and /generate_vllm are async def but call synchronous functions that block on a multiprocessing queue — and, in generate, a time.sleep(0.1) poll loop. The event loop is frozen for the duration, so uvicorn cannot accept connections or flush any in-flight SSE stream.

Fix: make the handlers def (FastAPI then runs them in its threadpool), or keep them async and await asyncio.to_thread(llm.generate, prompts).

Each streaming step re-tokenises the grown prompt and re-attends every prior position. n tokens cost n(n+1)/2 position-steps instead of n.

Fix: keep past_key_values per sequence (the worker already has a self.stream_states dict declared for exactly this, and never uses it), feed only the newest token id, and pass the cache back in each step.

In a mixed-length batch, position −1 for a short sequence is a pad token's logits. The attention mask prevents attending to padding; it does not change which index you read.

Fix: tokenizer.padding_side = "left", or gather at attention_mask.sum(-1) - 1 per row.

decode(..., skip_special_tokens=True) returns "" for EOS, which is compared against the string "</s>". Sequences end only when token_count > 20.

Fix: compare ids — next_token[i].item() == tokenizer.eos_token_id — and let max_tokens be a cap, not the mechanism.

Both execute_batch and execute_forward_batch block on the same result_queue, and replies carry no batch id. Concurrent use hands one caller the other's results.

Fix: a monotonically increasing batch_id on every message and a dispatch table (or a future per batch) on the way back.

LLMEngine.__init__ spawns a transformers worker and constructs a vLLM engine, which on a GPU pre-allocates ~90% of free VRAM by default. You pay both regardless of which endpoint is used.

Fix: pick a backend at construction time from config; if you must have both, gate the vLLM engine behind lazy initialisation and set gpu_memory_utilization.

requests_processing_loop catches every exception, prints it, sleeps, and continues — abandoning the remaining results of the current batch. A None from get_sequence (routine, on the step after cleanup) silently drops tokens for every other sequence in that batch.

Fix: handle the per-sequence case explicitly (if seq is None: continue) and let unexpected exceptions crash loudly with the batch id in the message.

The multi-model manager removes dict entries; it does not drop CUDA allocations. With the caching allocator holding freed blocks, "max 2 models" is not a memory bound.

Fix: an explicit unload() on the worker — delete the module, gc.collect(), torch.cuda.empty_cache() — before admitting the next model.

The worker loop handles a None sentinel that nothing ever sends. ModelExecutor.__del__ SIGTERMs the child mid-pass, and __del__ may not run at all on interpreter exit.

Fix: an explicit close() that sends the sentinel, join(timeout=…), then escalates — wired to FastAPI's lifespan shutdown rather than to garbage collection.

The incoming queues are unbounded and nothing expires. A client that disconnects from /generate (as opposed to /generate_stream, which cleans up in finally) leaves its sequences to be generated in full and thrown away.

Fix: bounded queues returning 429 when full, a per-sequence deadline checked each step, and a cancellation flag the loop honours.

ModelManager creates model_cache/ and never passes it as cache_dir. generate() returns prompt+completion because the prompt is never sliced off. multiprocessing.Lock guards a single-process global. asyncio.set_event_loop(loop) inside a coroutine already running on that loop. ModelEngine.workers declared at class scope and shadowed per instance. TorchVisionWorker ignores metadata.name. Debug prints in the streaming hot path.

What the map
doesn't show yet

Chapter 3 gets you a correct mental model of the request path. The stations that a production engine adds on top, roughly in the order you meet them:

  • Prefill/decode separation. Prefill is compute-bound and bursty; decode is memory-bound and steady. Mixing them in one batch means a long prompt stalls everyone's tokens. Chunked prefill splits the difference; disaggregated serving puts them on different machines entirely.
  • Speculative decoding. A small draft model proposes k tokens, the big model verifies them in one pass. Same output distribution, 1.5–3× fewer big-model steps on predictable text.
  • Quantisation. Decode is bound by weight bandwidth, so halving the bytes of the weights nearly halves the step time. FP8 on Hopper, INT4/AWQ/GPTQ below that, and a KV cache in FP8 to stretch the block pool.
  • Parallelism. Tensor parallel within a node for models that do not fit; pipeline parallel across nodes; expert parallel for MoE. Every one of them turns the ModelExecutor from "one worker" into "a collective".
  • Routing and autoscaling. Once there are many replicas, the router should be KV-aware: send a request to the replica that already has its prefix cached. That single decision beats most kernel work.
  • Observability that matches the physics. TTFT and inter-token latency, not just p99 request latency. Queue depth, batch occupancy, KV-block utilisation, preemption count. If you can't see batch occupancy you can't tell a throughput problem from a scheduling problem.

If you want to go deeper on any one line: the vLLM paper (Efficient Memory Management for Large Language Model Serving with PagedAttention, Kwon et al., SOSP 2023) for the memory argument, Orca (OSDI 2022) for the original iteration-level scheduling result that "continuous batching" is a name for, and the vLLM source itself — scheduler.py and block_manager.py are the two files that repay the most reading, and both will now look like enlarged versions of things you have already met.
